# 사용자·그룹 검색 — 1,000만 사용자 부하 테스트

측정일: 2026-11-22

## 결과

최적화한 실제 API에 총 **38,601건**을 요청했고, HTTP 오류·타임아웃·응답 검증 실패는 **0건**이었다. 동시 30요청에서 약 **663건/초**, **p95 64.6ms / p99 94.8ms**를 기록했다.

|---:|---:|---:|---:|---:|---:|---:|
| 1 | 2,180 | 72.6 | 11.3ms | 27.3ms | 36.7ms | 0 |
| 10 | 16,500 | 549.7 | 16.1ms | 31.0ms | 39.7ms | 0 |
| 30 | 19,921 | 663.1 | 41.7ms | 64.6ms | 94.8ms | 0 |

최적화 전 동일 데이터에서 8가지 검색을 순차로 한 번씩 호출한 결과는 **5.2~8.4초/요청**이었다. 이 8건은 비교용 기준 측정이며, 통계적으로 충분한 부하 표본은 아니다. 최적화 후 각 단계는 30초 동안 지속했다.

## 실제 데이터와 환경

- 사용자 **10,000,000명**, 그룹 **100,000개**, 멤버십 **10,000,000건**.
- 제한 스페이스의 권한 **100,000건**. 그중 64명이 스페이스 관리자이며 전역 관리자 우회 경로는 사용하지 않았다.
- 일회용 토큰 1,024개를 순환 사용. 실제 인증·권한 검사와 기본 토큰 요청 제한을 유지했다.
- 테스트 종료 시 DB 크기 **5.12GiB**, 유효한 검색 인덱스 **8개**.
- 별도 PostgreSQL 16.13 컨테이너: **4 CPU, 4GiB 메모리**, shared_buffers 512MiB, work_mem 8MiB.
- macOS/Apple Silicon의 Node 26.12.1, Next.js 15.5.20 production server, Prisma 6.19.3, 연결 풀 12개. 앱 프로세스의 CPU는 별도로 제한하지 않았다.
- 기존 데모와 다른 DB·포트·볼륨을 사용했다. 검색 전용 fixture는 UNLOGGED로 생성해 적재 시 WAL을 줄였고, 인덱스 생성 후 VACUUM ANALYZE를 수행했다.

## 변경한 동작

1. 한두 글자는 대소문자를 무시하는 **접두 검색**을 사용한다. SP-GiST 인덱스로 일치하지 않는 짧은 검색어도 빠르게 처리한다.
2. 연속된 문자·숫자가 세 글자 이상일 때 **부분 검색**을 추가한다. trigram GIN 인덱스를 사용한다.
3. 유형별 정확 일치·접두 일치 후보를 먼저 수집한다. 정확한 대상을 찾았거나 후보가 충분하면 추가 부분 검색을 생략한다.
4. 각 필드에서 제한된 후보만 가져와 중복을 제거하고 우선순위와 이름으로 정렬한다. 모든 일치 대상을 정렬하지 않는다. 반환은 사용자·그룹 각각 최대 10건이다.
5. 검색을 요청한 사람의 직접·그룹 권한만 읽어 관리자 여부를 판정하고, 결과의 현재 역할은 선택된 대상에 한정해 조회한다.
6. 그룹 멤버 수는 선택된 그룹별 최대 1,001행만 확인한다. 큰 그룹은 **“멤버 1,000명 이상”**으로 표시한다.
7. DB 문장 제한 1.5초와 트랜잭션 제한을 둔다. 제한 초과는 성공으로 숨기지 않고 503으로 반환한다. 이번 최종 측정에서는 제한 초과가 없었다.

인덱스를 항상 강제하지는 않는다. 흔한 검색어는 PostgreSQL이 순차 스캔을 선택해도 LIMIT에 도달하자마자 멈출 수 있다. 실행 계획에서 한 글자 접두 검색은 101행 검사 후 11건을 반환했고, 흔한 이메일 부분 검색은 11행만 읽었다. 존재하지 않는 짧은 접두 검색은 SP-GiST, 선택된 그룹의 멤버 수는 groupId/userId 인덱스를 사용했다.

## 검증과 해석 범위

- 단위 테스트 **125개**, 관리·검색 브라우저 회귀 테스트 **4개** 통과.
- 마지막 정확 일치 최적화 후 관련 브라우저 테스트 **2개** 재실행 통과.
- 타입 검사와 production build 통과.
- 동명이인/동일 그룹명, 현재 권한 표시, 사용자·그룹 권한 추가 및 변경, 직접·그룹을 통한 관리자 권한, 검색 접근 차단, 모바일·키보드, 실패 재시도, 큰 그룹 집계 제한을 확인했다.

이 결과는 **1,000만 사용자 데이터**의 검색 결과다. **1,000만 동시 사용자**나 그룹 1,000만 개를 시험한 것은 아니다. 합성 데이터와 단일 로컬 DB/앱의 짧은 closed-loop 부하이며, 캐시를 비운 콜드 부팅·장시간 운영·장애·복제·쓰기 부하는 측정하지 않았다. 브라우저의 입력 대기 200ms와 렌더링, Keycloak 로그인 시간도 제외했다. 실제 분포·네트워크·장비·동시 쓰기에서의 성능은 달라질 수 있다.

새 마이그레이션은 일반 CREATE INDEX를 사용하므로 큰 운영 테이블에 적용할 때는 유지보수 시간을 확보하거나 동일 인덱스를 CONCURRENTLY로 먼저 구축하는 배포 절차가 필요하다.
